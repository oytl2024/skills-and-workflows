# AI Repair and Runtime Boundaries

## Intent and Current Evidence

Make Repair an evidence-driven AI research loop rather than a rule-only parameter sweep. Routine operation remains Option Card plus Start/Stop. Preserve separate final Alpha submission authorization. Maintenance never silently expands live authority.

Current adapter derives actions from actions_for_check_summary and returns on the first RepairProgressPending. repair_runtime generates fixed variants. Advisory near_miss_interpretation is not consumed. The active run has a submitted flip-direction child for pwNbA8mq with no local completed identity. These are separate faults; HTTP200/Retry-After is not proof of a429 or platform completion.

## Approach

Use the existing read-only Codex executor and durable receipts, not an unrestricted autonomous coding agent. Compared with fixed-rule fallback, this actually delegates research judgment; compared with allowing arbitrary expressions/platform commands, a validated edit contract preserves reproducibility and authority. Do not introduce a new agent framework or UI layout.

## 1. AI Decision Contract

- A run-local Repair planner receives the checked parent expression/settings, failed metrics/checks, available local PnL evidence, prior children and comparative outcomes, and relevant knowledge snapshot evidence for data semantics, operator semantics, economic hypothesis, templates and repair levers.
- Missing evidence is explicitly marked unavailable. Do not invent a PnL assessment, fetch new platform knowledge, or claim a semantic match from a field name alone. Bound prompt input and reference source paths/digests; do not send the entire vault.
- Model output contains parent identity, diagnosed failure, economic explanation, one-change hypothesis, expected metric improvement, risks, and either a structured bounded edit or an explicit stop decision. Initially edits cover existing supported settings/direction plus operator transformations only when validated against local authoritative operator/type evidence and an allowed edit grammar. No free-form executable code, new fields, arbitrary programs or authority changes.
- AI reasoning must be medium or lower. Reuse the existing executor configuration and persist input/output/status. A failed, invalid or unavailable required judgment produces an actionable notification, never a silent deterministic substitution described as AI.
- The validator verifies lineage, scope, operator/type availability, supported parameter ranges, settings, uniqueness and remaining reserved allowance before publishing a plan. A valid model response alone is not a successful backtest.
- Persist immutable planned decisions and consumed decisions. Restart reuses the exact plan; new checked results create a new evidence-bound decision revision. Never re-plan an in-flight expression or re-charge its reservation.
- After a checked child, compare it with the parent and previous children; AI chooses another single-change test, accepts a candidate for formal checks, or stops that line. The existing total Repair allowance and mission budget bound iteration. Baseline checks precede expensive SELF/PROD checks; qualification remains evidence-based.

## 2. Independent Repair Scheduling

- Replace completed-prefix accounting with identity-keyed parent/child reservations and statuses: planned, submitted, waiting, checked, stopped or blocked. Existing immutable plans and source events are authoritative during migration.
- A waiting child yields its wake time while other independent parents with ready plans can advance within remaining allowance and the existing platform submission/concurrency policy. This is cooperative scheduling, not unlimited concurrent threads.
- Each slice handles bounded work. Poll only due saved URLs; completed AlphaIDs skip polling. When no legal work is ready, wait until the earliest eligible wake. Central429 cooldown blocks relevant new requests; an ordinary simulation wait does not block unrelated planning.
- Use existing submission gates, source locks, identity hashes and durable journals. Unknown POST remains reconciliation-required. Stop prevents new submissions and model dispatch promptly; preserve results/identities for Resume.
- A long-lived simulation receives a persisted age-based stalled-task diagnostic and a deduplicated maintenance notice, without inventing terminal failure or replaying its POST. Reuse an existing explicit timeout policy where suitable; otherwise expose one named policy constant and document its chosen value in the implementation plan.
- Repair remains incomplete while reserved children are pending. Publish each validated checked child durably once. Exhaustion with no useful child returns to the established bounded new-research-round loop, not a dead-end manual gate.

## 3. Runtime Exhaustion and Notifications

- Persist a distinct resource-boundary receipt for elapsed-time and step exhaustion. Record authorized limit, actual usage, stage, latest evidence, in-flight identities and recovery requirement without credentials.
- Send a bounded, event-triggered, deduplicated notice through the existing maintenance channel. Resource exhaustion is not automatically a code defect or repair authorization. Transport failure/uncertainty must be visible; no heartbeat/model polling and no blind uncertain-delivery replay.
- Console and CLI project the same exhausted next action and reason. Do not advertise Resume as progress when it can only exit immediately. Retain Stop and display that a separate runtime-authority decision is required.
- Repeated Start/Resume must neither reset elapsed time nor expand limits nor issue new WQB requests at an exhausted boundary. This change does not grant current-run time renewal. A renewal policy is a separate explicit human decision.
- Preserve historical resolved maintenance receipts; new boundary evidence must not overwrite or masquerade as a resolved code case.

## 4. Console Evidence

Keep existing layout and control locations. Show real AI state (queued/running/failed/validated/consumed), current hypothesis and reason, per-child waiting/check status, actual next wake and exhausted-resource reason. A checkpoint is not consumed until execution records it. Do not label local fake acceptance as live success.

## 5. Acceptance and Delivery

Add failing tests first for: validated AI output consumed by actual payload; unavailable/malformed/stale AI evidence; reusing decisions after restart; comparison-driven next iteration; one pending child while another progresses; fair reservation/no duplicate publication;429/Stop/unknown POST; existing plan migration; long-wait notification deduplication; time exhaustion during wait; immediate repeated Resume; notification failure; consistent Console actions.

Run an offline whole-flow fixture from multiple near misses through AI planning, staggered pending/completed simulations, restart, final checks or bounded round rollover, and resource-boundary notification. No live platform call is required to prove these contracts.

Update milestone architecture, todo handoff and user manual with implemented boundaries, run focused and full suites, and verify the loaded Console version only when no active job would be interrupted. End-to-end maintenance acceptance includes current boundary visibility; it does not imply permission to renew or resume live research.

## Explicit Non-Goals

No automatic Alpha submission, budget increase, elapsed-time reset, new platform capture, unrestricted coding agent, arbitrary template generation, new UI framework or automatic recurring monitor. Do not delete research evidence or existing knowledge material. Commit/push requires separate authorization.
